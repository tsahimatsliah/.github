## 4. Spec freeze v1.0 (2026-11-02)

**Statement.** The sixteen files `docs/spec/00-foundation-decisions.md` … `docs/spec/16-verify-register-and-index.md`, as they stand after the final consistency sweep of **2026-11-02**, are **spec v1.0**. They are the complete input for building the product: every number, ID, rule, acceptance criterion, default and open parent item is in its owning file, cross-references resolve (§3), and every unverified external fact is in the register (§2) with an owner, a method and a checkpoint. Rounds 1–2 and the final sweep are documented in `docs/review/` (`REVIEW-BRIEF.md`, `ROUND2-BRIEF.md`, `fable-issues-F1…F9.md`, `round2-R1…R7.md`, `final-sweep.md`) and in each file's `## Fable review changelog`.

**Rules for changes after v1.0.**

1. **Decisions change only through an ADR.** Any change to a binding rule, number, ID scheme, vendor, or default — in any spec — starts with an ADR in `docs/decisions/` using 13 §15's template (context, options, decision, consequences, re-evaluation trigger, sources). The ADR names the spec sections it changes and the 00 decision it touches.
2. **00 is updated in the same change.** If the ADR changes or adds a decision, the 00 decision index row and the full row are edited (or added with the next free id in that letter), the revision line at the top of 00 is bumped, and the ADR is cited in the row. A spec may never carry a rule that contradicts 00; if 00 is wrong, change 00 first.
3. **Owner-only edits.** A number or rule is edited in its owning spec (00 §J ownership map; §1 above); other specs cite it ("per 02 §x") instead of repeating it. Mirrors that already exist (e.g., 01's cap/bedtime mirrors) are updated in the same change and say so.
4. **IDs are stable.** Skill ids (`M.*`, `H.*`, `E.*`, 06 and 07 families), error codes (`EM.*`, `EH.*`, `ERR.*`/`SIG.*`), mechanic ids (`MX-*`), decision ids, `OPD-nn`, acceptance-criteria ids and event names are never renamed or reused. A retired id is kept in the owning spec's alias file (`packages/content/*/aliases.json`, `mechanics.aliases.json`) and marked deprecated; a new concept gets a new id.
5. **⟂VERIFY lifecycle.** A new unverified claim gets a `⟂VERIFY` marker with a one-line "how to verify" in the owning spec **and** a row in §2 of this file. Resolving one removes the marker in place, records the evidence in `docs/research-log/` (or the ADR), and updates the §2 row to "closed (date, evidence)". The register rows are never deleted.
6. **Changelogs.** Every edit to a spec appends a dated bullet under that file's `## Fable review changelog` (new heading `### Post-freeze changelog` on first use) naming the ADR. Round-1/2 and final-sweep entries are history and are not rewritten.
7. **Parent items.** New questions for the parent are added to 00's OPD table with a default (next free `OPD-nn`), then mirrored in 13 §16.2 and `docs/parent/questions.md`; a spec never introduces a parent question without an OPD id.
8. **Integrity gate.** Before a spec change is merged, the checks of §3 are re-run (the script's rules are documented there; it can be regenerated from them) and must stay at zero violations; the `pnpm verify` gate of 13 §9 covers the code side.
9. **Scope of freeze.** The research notes, review files and research logs are not frozen; they are evidence and history. The two research playbooks named in 00 E12 stay binding in the form 14 gives them.
