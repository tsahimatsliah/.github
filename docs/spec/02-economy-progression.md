## 0. עקרונות-על (מחייבים, ומהם נגזרים כל המספרים)

1. **הלמידה היא המשחק (C1), והאוסף הוא הלב (G1–G2).** התגמול העיקרי הוא מה שקורה בעולם: חבר שחולץ חוזר
   למחנה, חלק פסיפס נכנס למקום, החיה מתפתחת. המטבעות הם "דמי כיס" לביטוי עצמי, והם לא המנוע.
2. **שני סוגי "ערך", שלא מתערבבים לעולם:**
   - **מוני התקדמות (לא ניתנים להוצאה):** XP ורמות, חברים שחולצו, חלקי פסיפס, תגי מיומנות, שלבי התפתחות של
     חיות, דרגות במסלול העונה. הם עולים ואף פעם לא יורדים.
   - **כסף משחק (ניתן להוצאה):** מטבעות (K1, K2) ויהלומים (K1 בלבד). הם יורדים רק כשהילד/ה בוחר/ת לקנות.
   - הוצאה אף פעם לא מורידה התקדמות, ושום דבר שקונים לא מקדם למידה.
3. **קבלה, לא חוזה.** מטבעות ניתנים בסוף פרק כ"קבלה" שמתארת מה נלמד ("למדת 4 דברים חדשים, נזכרת ב-7"). אף
   פעם לא מכריזים מראש "עשה X ותקבל Y" (Lepper, D6). אין מונה מטבעות מרצד בזמן תרגול, ואין תגמול שקופץ אחרי
   כל תשובה. כך תשומת הלב נשארת על התוכן (מנגנון הקשב של Habgood, [N]).
4. **דטרמיניזם מלא.** אין אקראיות בשום ערך: לא בתיבות, לא בחנות, לא במכונת הקפסולות. ה"נדירות" נקבעת לפי מה
   שהרוויח את הפריט (D2).
5. **שום אובדן.** אין דעיכה, אין מס, אין "הפסדת", אין רצף שנשבר, אין תפוגה ואין ספירה לאחור (C5). היעדרות
   מוצגת כמנוחה.
6. **צפיפות תגמול יורדת עם הגיל ועם השליטה (thinning):** אצל K3 התגמול חושי, אצל K2 הוא "גושי מאמץ" ואצל K1
   הוא דליל ואינפורמטיבי. תרגול של חומר שכבר נשלט משלם מעט מאוד ואז כלום ([V] token-economy fading).
7. **שלושה מבנים גלויים בלבד** (מענה לחשש מ"עודף מערכות" ב-gap_audit):
   - **המסע (Map):** מפת האזורים והשלבים, מסלול העונה, אלבום העונות.
   - **השכונה שלי (My Neighborhood, 01 §10.1):** האווטאר והגיבור, חדר האוצרות, גן המיומנויות, החיות, החנות והצנצנות. זה המקום
     האישי היחיד שבו מוציאים מטבעות.
   - **המחנה המשפחתי (Camp, R-00):** המדורה, השכונות שמתמלאות בחברים שחולצו, היעד השבועי, הבוס והתרומות.

   כל מערכת במסמך הזה נמצאת באחד משלושת המבנים האלה, ואין מערכת שמסתובבת לבד.
8. **שוויון בלי השוואה (C6):** ילדים לא רואים מספרים של אחים. במחנה המשפחתי מוצג רק סך משפחתי. התגמולים
   מותאמים לגיל כך ששבוע טיפוסי "שווה" אותו דבר לכל ילד (ראו §12).

## 2. מטבעות, יהלומים ומדבקות: חוקי צבירה

### 2.1 טקסונומיית אירועים (מקור האמת: אירועי המנוע)

מנוע הלמידה (`packages/engine`) פולט אירועי למידה ליומן האירועים המצטבר (E6). מודול הכלכלה
(`packages/engine/economy`) הוא **פונקציה טהורה** שמקבלת אירוע, מצב ותצורה ומחזירה את המענקים:

```ts
type LearnEvent =
  | { t: 'item_answered'; itemId; skillId; firstTry: boolean; correct: boolean; hintUsed: boolean;
      workedExample: boolean; isReview: boolean; level: LevelId /* 08, via packages/shared/levels.ts */;
      rtMs: number; rtMsScored: number | null /* 08 §1.4: null כש-rtPolicy='ignore' (גן); §2.6 קורא רק את rtMsScored */;
      stretch: boolean; embodied: boolean /* G6: movement item */;
      provenance?: 'placement' | 'benchmark' | 'paper'; levelMode?: 'normal'|'placement'|'benchmark'|'review'|'boss'|'event' /* 01 §6.6 */;
      assisted?: 'parent' | 'sibling' | 'none' }
  | { t: 'episode_completed'; episodeId; coop: boolean; participants: ChildId[] }
  | { t: 'skill_level_changed'; skillId; from: LevelId; to: LevelId; reason: string }   // היה `skill_state_changed`; נושא את רמות 08 (C15), לא מצבי 02
  | { t: 'skill_level_reverted'; skillId; from: LevelId; to: LevelId; sessionId }       // 08 §10.5.3 אחרי `session_reattribute`: לא לוקחים כלום בחזרה (C5)
  | { t: 'delayed_check_passed'; skillId; gapDays: number }
  | { t: 'friend_rescued'; friendId; levelId; regionId }
  | { t: 'puzzle_piece_found'; pieceId; levelId; regionId }
  | { t: 'secret_level_cleared'; levelId; first: boolean }
  | { t: 'boss_defeated'; bossId; weekId; participants: ChildId[] }
  | { t: 'offline_mission_confirmed'; missionId; confirmedBy: ParentId }
  | { t: 'mentor_session_completed'; mentorId: 'K1'; menteeId }
  | { t: 'holiday_event_completed'; eventId }
  | { t: 'region_boss_defeated'; regionId }    // 01 §9.2; a region = a curriculum chapter
  // --- נוספו בסקירת Fable (01 §16.2, §21; 07 §2.2–2.3; 08 C11) ---
```

- **`DayKey` של כל אירוע** (לתקרות יומיות, לתשואה הפוחתת ולשבוע) נגזר מ-`ts + tzOffsetMin` של האירוע עצמו (11 §6.5),
  ולא משעון המכשיר בזמן ה-fold. כך אותו יומן נותן אותו מצב בכל מכשיר. **`tzOffsetMin` הוא ההיסט של אזור הזמן של עיר
  המשפחה** (`family.tz`; או של "עיר הנסיעה" `family_prefs.travel.city` כל עוד היא מוגדרת, 10 SET-01 / 01 DD-31) **בזמן
  האירוע, מחושב על המכשיר** — לא ההיסט של המכשיר (00-C3 גרסה 3: הגדרת יום אחת לכל האפליקציה, יום קלנדרי בעיר המשפחה,
  חצות; אותו `DayKey` משמש את 08 לתקרות ולכלל C11). המימוש היחיד: `packages/shared/dayKey.ts` (11).
- **`DayKey` מונוטוני לכל מכשיר** (`max(DayKey(ev), lastDayKeyOnDevice)`): הזזת שעון אחורה לא פותחת יום חדש ולא
  מאפסת תקרה (§18 UC-15).

**מצב הכלכלה הוא fold על יומן האירועים.** שום מכשיר לא שומר "יתרה" כאמת. כך סנכרון בין מכשירים (E6) לא מכפיל
תשלום: אירוע עם `id` שכבר עובד לא משלם שוב.

- **שמות על החוט (11 §5.8):** השמות כאן הם שמות המנוע (snake_case). על החוט השמות מנוקדים (`item.answered`, `world.rescue`,
  `skill.level_changed`, `skill.level_reverted`…); המיפוי היחיד הוא `toEngineEvent()` ב-`packages/shared/events.ts`. 02 לא
  מגדיר שמות חוט.
- **מה נשמר ומה נגזר (11 §5.8, F6):** 11 שומר **רק פעולות משתמש ואנומליות** (`econ.spend`, `chest.opened`, `inventory.equip`,
  `wishlist.set`, `econ.overdraft`). **מענקים, תכולת תיבות ו-`chest_earned` אינם אירועים נשמרים**: הם פלט נגזר של ה-fold מעל
  אירועי הלמידה. `chestId = hash(sourceEventId)` (D2): אותו אירוע-מקור נותן אותה תיבה בכל מכשיר, ולכן `applyEvent` אידמפוטנטי
  לפי `ev.id` של אירוע-המקור, לא לפי תיבה. `chest_opened{chestId}` הוא אירוע התיבה היחיד שנכתב (§6.3 כלל 7).
- **מצב השלב (`levelMode`, 01 §6.6; F9 GAP-13):** פריט שמגיע משלב `placement`/`benchmark` (או עם `provenance`) מקבל
  `grants = []` (§2.7 `placementProbe`/`paperProbe`); `friend_rescued` מתוך שלב כזה **כן** נספר לאוסף (00 G2), ולא מפעיל שום
  תיבה.
- **`skill_level_reverted`:** ה-fold **מתעלם ממנו לצורכי ארנק**: אף מטבע, יהלום, תג או XP לא נלקחים (`badgeNeverDowngrades`, C5).
  הוא משפיע רק על `paysOncePerSkill` — טריגר ששולם נשאר "שולם" (§4.1).

### 2.3 K2: קבלה ב"גושי מאמץ" (מספרים קטנים שהוא סופר)

כדי שהמספרים יישארו בטווח שילד בגן חובה סופר, ושלא ייווצר תשלום על כל תשובה:

```
coinsK2(episode) = episodeComplete(2) + min(chunksPerEpisodeMax(2), floor(correctOrRecovered / chunkSize(5)))
```

- `correctOrRecovered` סופר פריטים נכונים, כולל נכונים אחרי רמז, ואת חזרות ה-mastered המותרות.
- פרק טיפוסי (~14 פריטים) נותן 4 מטבעות.
- את הקבלה מציגים כמטבעות שנופלים אחד-אחד לצנצנת, עם ספירה קולית בנקבה ("אחת, שתיים, שלוש", B4). זה מקסימום
  4 מטבעות, כלומר ספירה קצרה.

## 3. XP ורמות

### 3.1 נוסחה

```
xpToNext(L) = round10( 250 + 80 · (L − 1)^1.2 )      L = 1..49
cumXp(L)    = Σ_{k=1}^{L−1} xpToNext(k)
```

**למה עקומה פולינומית עדינה (p=1.2) ולא מעריכית** (research-log §1):

- ברמות הראשונות היא מהירה: רמה 2 כבר בפרק הראשון.
- בחודש הראשון יש רמה כל 2–3 ימים.
- סביב רמה 30 יש רמה בערך כל שבועיים.

## 4. מיומנויות: מצבים, תגים ועץ מיומנויות

### 4.1 מצבים ותגים

```
locked → ready → introduced → practicing → proficient → mastered → retained
                                             (ארד)        (כסף)     (זהב)
```

> **מצבי טריגר פנימיים של הכלכלה (00-C15).** השמות שלמעלה הם **מצבי טריגר פנימיים** של מנוע הכלכלה בלבד. השמות
> הקנוניים שהילדים וההורים רואים הם של 08: `new / beginner / advancing / proficient / master`
> (חדש / מתחיל / מתקדם / שולט / מאסטר; תצוגת ילד: זרע / נבט / שתיל / עץ / עץ פורח). המיפוי מוגדר **פעם אחת** ב-
> `packages/shared/levels.ts` ושני המודולים (08 ו-02) מייבאים אותו:

| מצב 02 (פנימי) | רמת 08 (קנונית, C15) | איך נגזר |
|---|---|---|
| `locked` | — (קדם-מצב, בלי רמה) | דרישת-קדם לא ב-`proficient` |
| `ready` | — (קדם-מצב; "שוליים" של 08 §6.4) | דרישות-הקדם מולאו, אין תצפית |
| `introduced` | `new` | ≥1 פריט הוצג; אין תצפית מנוקדת או תצפית אחת |
| `practicing` | `beginner` או `advancing` | לפי 08 §5.1 (advancing: ≥5 תצפיות, דיוק ≥0.70) |
| `proficient` | `proficient` | 08 §5.1 |
| `mastered` | `master` | 08 §5.1 + בדיקה מושהית (D9) |
| `retained` | `master` + דגל `retained` | `master` **וגם** חזרה במרווח של **≥30 יום עברה בפועל** (`ReviewCard.maxPassedDays ≥ 30`, 08 §1.6). 08 פולט `review_rung_passed{skillId, rungDays}` בכל מעבר אמיתי (§5.4); הכלכלה מסמנת `retained` על הראשון עם **`rungDays ≥ 30`** ומשלמת פעם אחת. **לא** לפי ה-rung הנוכחי של הכרטיס: ב-K2 הסולם נגמר ב-30, ולכן "rung = 30" מתקיים כבר אחרי חזרת 14 הימים (באג שתוקן ב-08) |

- `skill_level_changed{from, to}` (§2.1) נושא את **רמות 08** (`LevelId`); הכלכלה **לא מחשבת מצבים בעצמה** אלא מייבאת
  `toEconomyState(level, ready, seen, maxPassedDays)` מ-`packages/shared/levels.ts` (08 §1.1א) וגוזרת ממנו את הטריגר
  (`rungUp` / `skillMastered` / `skillRetained`). `skillRetained` מופעל על `review_rung_passed{rungDays ≥ 30}` (ב-`reviewMode:'item'`
  08 פולט לכל כרטיס; 02 מצרף לפי `skillId`). `paysOncePerSkill` נבדק לפי `(childId, skillId, trigger)`, ול-`review_rung_passed`
  לפי `(childId, skillId, rungDays)` — כל ערך `rungDays` משלם לכל היותר פעם אחת. **אין שני סולמות בשום מסך** (C15).
- `skill_level_reverted` (08 §10.5.3, אחרי "זה לא היה {name}"): הרמה יורדת במודל של 08, **והכלכלה לא לוקחת דבר בחזרה** —
  לא מטבעות, לא יהלומים, לא תג, לא XP (C5, `badgeNeverDowngrades`). הטריגר נשאר "שולם" (`paysOncePerSkill`), ולכן עלייה
  חוזרת אחר כך לא משלמת פעם שנייה. נבדק ב-§14.1.
- ירידת רמה ב-08 (למשל `master → proficient` אחרי כישלון בבדיקה מושהית) **לא** מורידה תג, לא לוקחת יהלום ולא מחזירה
  XP (`badgeNeverDowngrades`). היא רק מאפשרת ל-`rungUp`/`skillMastered` להשתלם שוב? **לא.** כל טריגר כלכלי משתלם **פעם
  אחת לכל מיומנות לכל חיים** (`paysOncePerSkill`), ולכן עלייה חוזרת אחרי ירידה לא משלמת שוב (בדיקה ב-§14.1).
- **"נשלט" (mastered)** לפי ההגדרה האחת (gap_audit D9):
  - ≥85% ב-8 הניסיונות הראשונים האחרונים;
  - 3 האחרונים בלי רמז;
  - פרוס על פני ≥2 ימים;
  - ובדיקה מושהית נכונה אחרי ≥3 ימים.
- **"נשמר" (retained):** עבר את שלב החזרה של 30 יום.
- **שם התג = שם המיומנות.** דוגמאות: "לוח הכפל של 7", "קריאת מילים בקמץ ופתח", "סופרים עד 20".
  - כל תג מציג גם את התהליך: "תרגלת ב-6 ימים שונים".
  - K2 שומע את שם התג בקול.
- **תג לא יורד דרגה לעולם** (`badgeNeverDowngrades`). אם הייתה מעידה בחזרה, המיומנות מקבלת ניצוץ "מוכן לפרוח
  שוב" (gap_audit D19), והתג נשאר.

### 4.2 עץ המיומנויות = "גן המיומנויות" בשכונה

- **תחום (domain) = עץ, ענף (strand) = ענף.** התחומים:
  - חשבון
  - קריאה בעברית
  - אנגלית
  - עולם ומדע
  - חשיבה
  - לב וחברים (SEL)
- **כל מיומנות היא צמח לפי רמת 08 (00-C15, תצוגת ילד אחת בלבד: זרע / נבט / שתיל / עץ / עץ פורח), והתג הוא שכבה מעל
  (F5 #1):** האייקונים מיובאים מ-`packages/shared/levels.ts` (`LEVEL_CHILD_HE`, 08 §1.1א); 02 לא מגדיר סולם צמחים משלו.
  - `locked` (קדם-מצב): שלט "באתר בנייה" עם דמות ידידותית (לא מנעול), בלי צמח.
  - `ready` (קדם-מצב): ערוגה ריקה שזוהרת קלות ("אפשר לשתול"), בלי צמח.
  - `introduced` = רמה `new`: **זרע**.
  - `practicing` = `beginner`: **נבט**; = `advancing`: **שתיל** (לפי הרמה שמגיעה מ-08, לא לפי 02).
  - `proficient` = `proficient`: **עץ** + תג **ארד** כשכבה.
  - `mastered` = `master`: **עץ פורח** + תג **כסף** כשכבה.
  - `retained` = `master` + דגל `retained`: **עץ פורח** + תג **זהב** כשכבה (הצמח לא משתנה; רק התג).
  - ירידת רמה ב-08 מורידה את הצמח (למשל עץ פורח → עץ), **אבל התג נשאר** (`badgeNeverDowngrades`): עץ עם תג כסף הוא מצב
    תקין ומוצג כ"מוכן לפרוח שוב".
- **חזרה שהגיע זמנה:** הצמח זוהר ("מוכן לפרוח"). **אין קמילה, אין נבילה ואין ירידה בצבע.**
- **הקשה על צמח:** פותחת את התג. אם היא בשלב ready או חזרה, היא מציעה "לשחק עכשיו" כבחירה חופשית ולא כלחץ.
- **גרף המיומנויות עצמו** (צמתים, דרישות קדם) מוגדר במפרט המנוע. המסמך הזה מגדיר רק את המיפוי החזותי ואת
  התגמולים.

### 5.2 כללים

1. **חילוץ דורש פעולת למידה** (`rescueRequiresLearningAction`, 01 P-1): לפתוח כלוב בפתרון, לקרוא שלט, לספור,
   לומר משהו באנגלית, למיין, או לעשות פעולת תנועה (G6). חבר סודי נמצא בזכות סקרנות, ואז דורש פעולת למידה קלה.
2. **חילוץ לא יכול להיכשל** (`rescueCannotFail`): מגן התסכול מוביל לרמז ואחר כך לדוגמה מודרכת, והחבר משתחרר.
   התגמול הוא על המאמץ, לא על הצלחה בניסיון הראשון.
3. **הסקרנות מתוגמלת תוך שניות (G1).** כל פינה נסתרת נותנת משהו: חבר, חלק פסיפס, דף יומן (01), או "ביצת הפתעה"
   קטנה של אנימציה וצליל, בלי מטבע.
4. **חברים וחלקים לא מוציאים אותם.** הם נספרים, מוצגים וחיים בשכונה של הילד שחילץ אותם (01 §10.1).
5. **שום דבר במסלול התוכנית לא חסום מאחורי איסוף.** השלב הבא במפה נפתח לפי התקדמות למידה. אזורים נפתחים לפי
   רמת המדורה ומוכנות המיומנויות (01 §2). איסוף פותח **בונוס** בלבד: מבני שכונה, שלבים סודיים, סדרות קפסולות
   וקישוטים. **איסוף פותח "עוד כיף", לא "עוד גישה ללמידה".**
6. **אין החמצה.** כל שלב ניתן לשחק שוב לנצח. חברים שלא נמצאו מוצגים כצלליות על כרטיס השלב ובלוח החברים האבודים
   ("4/7"). שלבי חג עוברים ל"תיבת החגים" במחנה וזמינים לתמיד (01 §13).
7. **רמזים:**
   - "האף של החיה" מצביע על סוד אחרי 20 שניות בלי התקדמות, או 45 שניות בלי שנמצא סוד (01 §6.2).
   - בשלב שמשחקים שוב: ל-K2 שובל ניצוצות לחברים שנשארו, תמיד; ל-K1 "רדאר" לפי בחירה.
   - **רמזים חינמיים תמיד, ואף פעם לא נמכרים** במטבעות.
8. **התקדמות ממומשת ביושר (endowed progress) [BK].** 01 §10.3 פותח את חדר האוצרות עם 3 חברים מהפתיחה. כלל
   הכלכלה: שלושתם **מחולצים בפועל** על ידי הילד בפתיחה, בפעולות אמיתיות וקלות. זה לא מילוי מזויף
   (`endowedProgress.mustBeActiveRescues`).

### 5.3 שלבים סודיים

יש שני סוגים, משלימים:

- **(א) יציאות סודיות בתוך שלבים (01 §6.1):** הסקרנות מגלה אותן.
- **(ב) שלבים סודיים לפי אבני דרך באוסף** (ההגדרה כאן):

| טריגר | שלב | תוכן |
|---|---|---|
| 50% מחברי האזור חולצו | `secretA`: "המערה הסודית" | רמיקס משולב של מיומנויות האזור (חזרה מרווחת ומעורבבת) עם גימיק חדש (G3) |
| הפסיפס האזורי הושלם | `secretB`: "שער הפסיפס" | התמונה שהושלמה (01: דף יומן + קישוט למדורה) הופכת גם לפורטל; שלב קצר ומפתיע |
| 100% חברים + חלקים (K1 בלבד) | `goldenRemix`: "רמיקס זהב" | גרסת אתגר (Stretch) של האזור, opt-in |

- **סיום ראשון של שלב סודי:** תיבת עץ עם פריט ייחודי לאזור, כמו כובע מהמערה. בנוסף משתלמים תגמולי הלמידה
  הרגילים.
- **שלבים סודיים הם ערך פדגוגי.** הם המקום הטבעי לחזרה מעורבבת (interleaving) של מיומנויות שכבר נשלטו.
- **ל-K3 אין שלבים סודיים.** במקומם, כל 5 חברים מוסיפים צעצוע חדש בחדר המשחקים (01).

### 5.4 חדר האוצרות (בתוך "בית החברים" בשכונה, 01 §10.3)

01 מגדיר את החדר: מדף לכל **מין** של חברים, צלליות, וסט מין שהושלם שווה תג על שם קבוצת המיומנות והתפתחות של
החיה. הכלכלה מוסיפה:

- **פס התקדמות לכל מדף** (goal-gradient [BK]: מאמץ עולה ככל שמתקרבים ליעד).
- **סט מין שהושלם** (`speciesSetComplete`): חגיגת T3 + תג סט + תיבת כסף (K1) או תיבת עץ (K2).
  - **[D]** החיה מתפתחת לפי שליטה (§8.2) ולא לפי סט. סט שהושלם נותן לחיה **אביזר** ולא שלב התפתחות. כך ההתפתחות
    נשארת קשורה לשליטה (D4), ולא ל"מצאתי את כולם".
- **קירות:** תמונות הפסיפס, קיר התגים (§4), גלריית החיות ואלבומי העונות. כולם במקום אחד, כדי למנוע עומס מערכות.
- **אבני דרך אישיות:** כל 100 חברים שחולצו נותנים כותרת וכובע. הכותרות מתארות פעולה ("100 חברים חזרו
  הביתה"), לא תכונה.
- **בלי FOMO:** אין צלליות "מוגבלות בזמן", ואין צללית של משהו שכבר אי אפשר להשיג.

### 5.5 השכונה מתמלאת בחיים: פתיחת מבנים לפי חילוצים (G2, 01 §10.2)

- **החברים שחולצו גרים בשכונה של הילד שחילץ אותם.** מבנים בשכונה נפתחים לפי מספר החילוצים **של הילד עצמו**.
  זה "מודל Astro": שלט עם צללית של המבנה הבא ו"עוד 4 חברים", בלי מחיר ובלי מכירה.
- **בעיית קצב שהסימולציה מצאה.** בקצב החילוץ הצפוי (§12: K1 ~40, K2 ~39 בשבוע), הספים הנוכחיים של 01 (K2: 5–150,
  K1: 8–240) **פותחים את כל 7 המבנים תוך 4–6 שבועות.** אחר כך החילוצים כבר לא "בונים" כלום.
- **ההצעה (ברירת המחדל ב-config, `neighborhoodThresholds`; ראו §17):**

| מבנה (01) | `id` | K2 | שבוע צפוי K2 | K1 | שבוע צפוי K1 |
|---|---|---|---|---|---|
| בית החברים (+ חדר האוצרות) | `friendsHouse` | 5 | 0.1 | 8 | 0.2 |
| צריף המוזיקה | `musicHut` | 20 | 0.5 | 30 | 0.8 |
| אוהל התחפושות | `costumeTent` | 50 | 1.3 | 80 | 2.0 |
| גן הגוזלים | `chickGarden` | 100 | 2.6 | 150 | 3.8 |
| תיאטרון הסיפורים | `storyTheater` | 160 | 4.1 | 240 | 6.0 |
| מגדל הכוכבים | `starTower` | 240 | 6.2 | 360 | 9.0 |
| סדנת היוצרים | `creatorsWorkshop` | 350 | 9.0 | 520 | 13 |
| **+ מבנה עונתי חדש בכל עונה** | `perSeasonNewBuilding` | +120 | | +180 | |

- **מה נשמר:** המבנים שהם תשתית (בית החברים, אוהל התחפושות, גן הגוזלים) נשארים מוקדמים, ומה שמתארך הוא "הזנב".
- **מבנה עונתי חדש** נותן לחילוצים משמעות לתמיד, כמו מבנה חג ליד כיכר המחנה.
- **K3 תורם חברים באמת** (3 בכל שלב, ~18 בשבוע) לחדר המשחקים שלו: צעצוע חדש כל 5 חברים. זו תרומה גלויה ובעלת
  משמעות לפעוטה, בלי שום מטבע.
- **ערבי הגנה על המדורה (G5, 01 §9.5):** כוחות שמגיעים מלמידה. אם הצללונים "עוברים", האש מתעמעמת ו"מחר נוסיף
  עצים". **שום שדרוג, חבר, מבנה או עץ לא הולך לאיבוד, לעולם.**
- **ניצוצות (sparks, 01 §11.1)** הם משאב שקיים רק בתוך הפרק ומתאפס בסופו. הם **לא** חלק מהכלכלה, ולא מומרים לעולם.

### 5.6 היחס בין חילוצים לבין מטבעות, יהלומים ותיבות

| ערך | ניתן להוצאה? | מאיפה מגיע | מה הוא פותח או קונה |
|---|---|---|---|
| חברים שחולצו | לא | פעולות למידה בשלבים | מבני שכונה (§5.5), `secretA`, אבני דרך אישיות, תיבות אזור, צעצועים (K3) |
| חלקי פסיפס | לא | פינות נסתרות + פעולת למידה | `secretB`, סדרות במכונת הקפסולות, מסגרות לקיר |
| XP | לא | כל פעולת למידה | רמות, מסלול העונה |
| מטבעות | כן | קבלות, תיבות, רמות, עונה | קוסמטיקה, בנייה בשכונה, פינוקים לחיה, קפסולות, תרומה למדורה |
| יהלומים (K1) | כן | אבני דרך בלבד (§2.5) | פריטים נדירים, תרומה למדורה |
| תיבות | — | אבני דרך (כולל אבני דרך באוסף) | מכילות מטבעות, יהלומים ופריטים ידועים מראש |

- **אבני הדרך באוסף משלמות דרך תיבות** (§6):
  - 50% מהאזור: תיבת כסף.
  - פסיפס הושלם: תיבת כסף.
  - 100% מהאזור: תיבת זהב.
- **חילוץ בודד לא משלם מטבעות.** כך אין "חיפוש כסף" שמתחרה בסקרנות. החבר הוא התגמול.
- **הלבשת חברים** (`friendOutfits`, K1 מרמה 9): בור מטבעות חמוד. קונים כובע ומלבישים חבר שחולץ, והוא מסתובב
  איתו במחנה.

### 5.7 מכונת הקפסולות (במקום Gatcha) [BK על המקור]

- מכונה במחנה, נפתחת ברמה 4 (K1) או 10 (K2).
- **מחיר קפסולה:** 60 מטבעות (K1), 6 (K2).

- זה גם בור מטבעות בקצב קבוע.

### 6.3 כללי תכולה קבועה (D2)

1. **התכולה נקבעת בזמן הזכייה** כפלט נגזר של ה-fold: `chest_earned{chestId, trigger, contents}` עם `chestId = hash(sourceEventId)`
   (11 §5.8, F6). זה **לא** אירוע שנשמר ביומן: כל מכשיר שמקפל את אותו אירוע-מקור מקבל את אותה תיבה עם אותה תכולה (פריטים,
   מטבעות, יהלומים), כי המסלולים (`track:*`) דטרמיניסטיים והמצב הוא fold.
2. **"מסלולי תיבה"** (`track:wood`, `track:silver`, …) הם רשימות פריטים מסודרות ומאוצרות. כל תיבה נותנת את
   הפריט הבא ברשימה שהילד עוד לא מחזיק. **המסלול גלוי** בחדר האוצרות: "התיבה הבאה מכילה…". בתיבת זהב הילד בוחר 1
   מתוך 3 פריטים שמוצגים מראש (אוטונומיה).
3. **בלי כפולים** (`noDuplicates`). אם מסלול נגמר, התיבה מכילה מטבעות קבועים (K1: 25, K2: 4). זה מוצג מראש.
4. **תצוגה מקדימה לפני פתיחה** (`previewBeforeOpen`): התיבה מוצגת עם צללית הפריט ותווית ("בפנים: כובע פיראט +
   40 מטבעות"). ל-K2 התווית מוקראת.
5. **אין טיימרים, אין משבצות מוגבלות ואין תפוגה.** אפשר לפתוח מיד או לשמור ב"מדף האוצרות" (למשל כדי לפתוח עם
   אבא). התג על המדף מראה מספר שקט, בלי נקודה אדומה מהבהבת.
6. **התנגשות סנכרון** (שני מכשירים אופליין זכו באותו פריט במסלול): בזמן המיזוג התיבה המאוחרת נשארת עם הפריט.
   בחשיפה מוצג "כבר יש לך את זה, קיבלת במקומו X מטבעות" (מחיר band A). **פריט שנכנס לאוסף לא נלקח לעולם.**
7. **חשיפה אידמפוטנטית** (01 §16.2, §21 UC-14): התיבה קיימת ברגע שאירוע-המקור ביומן (כלל 1, נגזר); `chest_opened{chestId}`
   הוא **אירוע התיבה היחיד שנכתב**, **בתחילת פעימה 6** (חשיפה). ה-fold מעניק את התכולה **רק** על `chest_opened`. אפליקציה
   שנהרגה לפני פעימה 6 → התיבה נשארת על המדף סגורה; אחרי → בהפעלה הבאה מנוגנת רק פעימה 8 (איסוף, ≤0.7 שנ'). אין נתיב
   שמעניק פעמיים, גם כששני מכשירים מקפלים את אותו אירוע-מקור (אותו `chestId`).
8. **פתיחה אוטומטית** (נגישות, 01 DD-39): בהגדרת "פתיחה אוטומטית" או ב-Reduce Motion, פעימות 3–5 מתכווצות לזוהר
   אחד של 300ms ו-`chest_opened` נכתב אוטומטית אחרי 4 שניות על המדף הפעיל. הדרגה והתכולה לא משתנות.

### 6.4 למה לא צריך pity או ערבות

מנגנוני pity (למשל ב-Genshin) נועדו לחסום את **השונות** של מערכת אקראית: הם מבטיחים שרצף ארוך של מזל רע ייגמר.
כאן **השונות אפס**. אותו טריגר נותן תמיד את אותה דרגה ואת אותה כמות, והפריט הוא הבא ברשימה גלויה. אין "מזל רע"
שצריך לתקן. הערבות היא המנגנון עצמו. לכן אין צורך גם בהצגת סיכויים: אין סיכויים להציג.

### 6.5 כוריאוגרפיית חשיפה (לכל פעימה)

**כלל-על:** **הדרגה מוצגת מהפריים הראשון ולא משתנה.** אין אנימציית "שדרוג צבע". זה ההבדל מ-Starr Drop, שבו

### 7.3 "רוטציה" שתמיד חוזרת

00-D3 קובע: "פריטים מתחלפים אבל תמיד חוזרים, בלי ספירה לאחור". היישום כאן מחמיר יותר:

- **הקטלוג קבוע** (`catalogPermanent`): כל פריט שנכנס נשאר לתמיד וזמין לקנייה. **שום פריט לא עוזב.**
- **"חלון הראווה"** (`showcase`) מציג 6 פריטים מתוך הקטלוג ומתחלף **פעם בשבוע, ביום ראשון**.
  - **לא בכל יום:** ריענון יומי הוא מנוף חזרה יומי ופיתיון (Radesky, gap_audit).
  - בלי הנחה, בלי ספירה לאחור ובלי "אחרון במלאי".
  - הוא נותן רעננות בלבד.
- **פריטי חג** מוצגים בחלון הראווה בזמן החג, ונשארים בקטלוג אחריו.
- **רמות פותחות פריטים.** צלליות של פריטים שעוד לא נפתחו מוצגות עם "נפתח ברמה 12". זו מפה, לא לחץ.
- **ביטול קנייה:** אפשר לבטל תוך 10 דקות בלחיצה אחת (`refundWithinMinutes`). ההורה יכול לבטל מתי שהוא רוצה.
  - **מה קורה כשההורה מבטל פריט שכבר לבוש או מוצב** (F9 GAP-38): הפריט **מוסר בשקט**: בגד/כובע → חוזרים לתלבושת הקודמת (או
    לברירת המחדל), קישוט/שרטוט → מוסר מרשת השכונה (`neighborhood_layout` מתעדכן), אביזר חיה → מוסר. המטבעות חוזרים
    **לצנצנת שממנה שולמו** ("להוציא"), הפריט חוזר לקטלוג כזמין. הילד רואה **פתק ניטרלי בתיבת הדואר** בפרק הבא ("הפריט X
    חזר לחנות והמטבעות חזרו לצנצנת"), **בלי אנימציית "נלקח"**, בלי צליל שלילי ובלי הודעה בזמן אמת. ביומן: `econ_spend{refunded:true, by:'parent'}`.
  - **"החנות סגורה"** (10 W-ECO-06; F9 GAP-42): הכוונה **רק** לחלונות "האפליקציה ישנה" ולשעת השינה של הילד (01 §15.1, 10 SET-02),
    לעולם לא לשעות השקט של התראות ההורה. בפועל החנות פשוט לא נגישה כשהאפליקציה ישנה; השלט "החנות ישנה" מופיע רק במצב
    `camp_asleep` של K1 (01 §15.1).

- **אין העברות בין אחים.** כך נמנעים לחץ, "חובות" וויכוחי הוגנות (C6). הנתינה היא תמיד למשותף.
- **משיכת-יתר ממיזוג (11 §6.5 `econ.overdraft`; F9 GAP-10):** אם היתרה המינימלית של השבוע **שלילית** בפרויקציה (שתי קניות
  אופליין בשני מכשירים), הבסיס לבונוס הוא `max(0, minBalance)` = 0, כלומר **שבוע עם משיכת-יתר לא משלם בונוס** ואף פעם לא
  "בונוס שלילי". הבונוס חוזר בשבוע הבא כרגיל. ב-config: `saveBonus.basis: "minBalanceDuringWeekClamped0"`.
- **הטענה הלימודית צנועה** [V/N]: זה גשר משחקי לצנצנות האמיתיות בבית. בחבילת ההדפסה יש דף "3 צנצנות".

## 10. יעד משפחתי שבועי

### 10.1 נוסחה

```
DayKey(ev)    = calendarDate(ev.ts, family city tz)   // §2.1 / 00-C3: יום קלנדרי (חצות) בעיר המשפחה או בעיר הנסיעה; אין גבול "04:00"
week          = Sunday 00:00 → Saturday 23:59 (family city tz)
availableDays = 7 − |{Shabbat}| − |{yom tov in week}| − |{parent-declared rest days}|
effTarget(c)  = (availableDays == 0 || c.paused || c.excludedFromGoal) ? 0 : min(target(c), ceil(availableDays × 0.6))
adventureDay(c, d) = c completed ≥1 episode on day d   (K3: ≥1 lap episode; co-op episode counts for every participant)
                     OR an episode closed as 'abandoned'/'profileSwitch' with levelsCompleted ≥ 1 (01 DD-27; §18 UC-05)
progress = Σ_c min(days(c), effTarget(c) + overshootAllowance(1))
goal     = Σ_c effTarget(c)
met      = goal > 0 && progress ≥ goal
```

- **יעדים:** K1 3, K2 3, K3 2. אם ההורה מוציא את K3 מהיעד, היעד שלו 0. **ילד מושהה** (`profile.paused`, 08 §10.5.8, 10 FAM-03)
  מקבל `effTarget = 0` בדיוק כמו ילד שהוצא מהיעד (F5 #3): הוא לא נספר ב-`goal`, ימי משחק שלו (אם ישנם) נספרים כבונוס, ואין
  לו תיבת יעד; חזרה מהשהיה באמצע שבוע → היעד שלו מצטרף מהשבוע הבא.
- **גבול היום (00-C3 גרסה 3; F9 GAP-44 נדחה):** הגדרת יום **אחת** לכל האפליקציה: `DayKey` = יום קלנדרי בחצות **בעיר המשפחה**
  (או בעיר הנסיעה כשהוגדרה, 01 DD-31), מחושב מ-`ts + tzOffsetMin` של האירוע (§2.1), מונוטוני לכל מכשיר. אותו `DayKey` משמש
  לתקרות של 08, לתשואה הפוחתת, להפתעה היומית, ל-`adventureDay` ולכלל "≥2 ימים" של C11. אין גבול 04:00: נעילת השינה (01 §15.1)
  הופכת את פער חצות ללא-רלוונטי לילדים. המימוש היחיד: `packages/shared/dayKey.ts` (11).
- **המשמעות של `overshootAllowance = 1`:** אח שמשחק יום נוסף יכול "לפצות" על יום אחד של אח חולה, אבל לא יותר. כך
  היעד נשאר משפחתי, ואף ילד לא סוחב לבד.
- **ימים שמשחקים בהם בשבת או בחג** (אם המשפחה ביטלה את הנעילה, B7) נספרים כבונוס להתקדמות, ולא נדרשים.
- **שבוע שבו `availableDays = 0`** (למשל רצף חגים) מוצג כ"שבוע מנוחה", בלי יעד.

### 10.2 תצוגה ותגמול

- **תצוגה:**
  - במחנה יש משבצות "עצים למדורה" שמתמלאות.
  - רק הסך מוצג, בלי שיוך לילד.
  - **בלי "נשארו X ימים"** (`showDaysLeft: false`).
- **כשהמשפחה עומדת ביעד:**

  - K1 ו-K2 מקבלים תיבת זהב (ב-K1 עם 2 יהלומים); K3 מקבל מעטפת הפתעה.
  - +20 עצים.
  - הודעה להורה עם הצעה לפעילות משפחתית (§11).
- **אם המשפחה לא עמדה ביעד: לא קורה כלום.** אין הודעה, ובראשון מתחיל שבוע חדש. המדורה "נחה".
- **אין יעד כפול ואין "יעד-על".** אין הסלמה של חובות.
- **רצף:** אין רצף יומי לאף אחד (C5). חוגגים **חזרה** ("איזה כיף שחזרת"), לא ימים ברצף.

### 10.3 שבת, חגים וימי זיכרון

- **ימי מנוחה** (`restDays`) מוצאים מ-`availableDays`: שבת, ימים טובים, ימי מחלה או טיול שההורה מכריז.
- **שבת `soft` (00-B7; F5 #4):** בתוך החלון `[הדלקה−30, הבדלה+30]` מ-`packages/shared/calendar.ts` (`@hebcal/core`) `applyEvent`
  מחזיר **אפס מענקי מטבעות, יהלומים ותיבות לכל אירוע, בלי תלות בטקסט המצב** (גם אם ה-UI "חושב" שזה יום רגיל): הבדיקה
  נעשית ב-fold לפי `ts` של האירוע, לא לפי דגל של המסך. XP נספר (08 §6.10: ראיה היא ראיה). אבן דרך נדחית ל"אחרי החלון"
  (§18 UC-09). **החלון חל לפי תחילת המפגש** (01 §15.4; F9 GAP-14d): מפגש ש-`session.started` שלו לפני תחילת החלון נספר
  ומשולם במלואו בקבלה שלו, גם אם הקבלה נופלת בתוך החלון (`edgeRules.shabbat.appliesBySessionStart: true`); מפגש שהתחיל
  בתוך החלון כפוף לו. ב-`full` אין אירועים כלל. בדיקה: §14.1 "שבת".
- **ימי יום טוב:** ראש השנה (2), יום כיפור, סוכות ושמחת תורה, פסח ראשון ושביעי, שבועות.
- **טבלת התאריכים:** טבלה מאומתת ידנית מצורפת לאפליקציה (נוצרת ב-build מ-Hebcal ונבדקת), באותו עיקרון כמו B4.
- **ימים "רגועים"** (`calmDays`): יום השואה, יום הזיכרון, תשעה באב.
  - נספרים כימים רגילים.
  - אין בהם אירוע חגיגי, תיבות לא נפתחות אוטומטית, והחגיגות מוגבלות לדרגה "קטנה".
- **אירועי חג** (`holidayEvents`, רשימת האירועים ב-01 §13.2). דוגמה: חנוכה, "שמונה לילות של אור". בכל לילה שבו
  המשפחה משחקת נדלק נר בחנוכייה שליד המדורה.
  - **"אוצר האירוע"** ניתן אחרי השלמה של ≥60% משלבי האירוע (01 §13.3; `eventTreasureAtLevelShare`). התכולה ידועה
    מראש. אצל K1 זה אוצר אגדי עם 3 יהלומים, אצל K2 תיבת זהב, ואצל K3 מעטפת הפתעה.
  - **אין "מטבע אירוע"** (`noEventCurrency`).
  - **האירוע נשאר ניתן להשלמה גם אחרי החג.** השלבים עוברים ל"תיבת החגים".
  - פריטי החג נשארים בקטלוג.
  - **כל אירוע מזרים מטבעות רק יחד עם פריטי חג בחנות** (`matchedSinkRequired`).
  - אין אירועים ביום כיפור ובימי הזיכרון (QD).

## 11. תגמולים בעולם האמיתי (מודול הורים)

1. **מאחורי שער הורה בלבד** (Face ID או PIN, E7).
2. **ההורה מגדיר פעילויות משפחתיות** ("אופים יחד", "טיול לפארק", "ערב סרט", "מדורה אמיתית בחצר"). ברירת המחדל
   היא חוויות, לא חפצים. ההורה יכול להוסיף חפצים, אבל המערכת לא תציע אותם.
3. **לא מתומחר במטבעות** (`pricedInCoins: false`).
   - המרה של מטבעות לפרסים אמיתיים הופכת אותם ל"כסף" ומגבירה את סיכון ההצדקה-היתר (gap_audit D1).
   - זה סותר את הדוגמה "500 מטבעות" בטבלה 8 של דוח v1. ראו §16.
4. **הקישור הוא למאמץ ולעקביות, לא לביצוע.** טריגרים להצעה (להורה בלבד):
   - "המשפחה עמדה ביעד השבועי 3 פעמים העונה";
   - "K1 סיימה את אלבום העונה";
   - "5 משימות בעולם האמיתי החודש";
   - או שיקול דעת של ההורה.
5. **לא מוכרז מראש לילד, לעולם** (D6). אסור "אם תסיים 5 שיעורים תקבל גלידה". אחרי שההורה מחליט, האפליקציה יכולה
   להציג לילד כרטיס "הפתעה מאבא ואמא: נאפה יחד!" כתגמול **לא צפוי** (Lepper: תגמול לא צפוי לא פוגע).
6. **קצב:** הצעה אחת לכל היותר כל 14 יום. ההורה יכול לכבות לגמרי.
7. **הוגנות:** ההצעות הן משפחתיות או שוות לכל הילדים. אין פרס אמיתי לילד אחד על "יותר" מהאח.
8. **ההורה רואה במסך את הרציונל:** "למה לא מטבעות תמורת פרסים?" ושני משפטים על Deci ו-Lepper.

  מוסיפים פריטים חדשים ברצועות C ו-D. **לא מורידים הכנסה ולא לוקחים כסף.** אם הילד חוסך בכוונה ("לחסוך" גבוה),
  זה לא אזעקה. זו הצלחה.
- **אזעקת הצדקת-יתר** (`overjustificationAlarm`): ראו §14.3.

### 12.4 אינווריאנטים (נבדקים בסימולציה ב-CI)

1. טיפוסי: K1 קונה פריט D תוך 2–5 שבועות; K2 תוך 2–5 שבועות.
2. היחס בין קבלות לבין אבני דרך הוא 35–65% לכל צד. כך ההכנסה קשורה גם למאמץ וגם לשליטה.
3. כבד חלקי טיפוסי ≤ 1.8 (התשואה הפוחתת עובדת).
4. מסלול העונה הטיפוסי מסתיים ב-50–75% מאורך העונה.
5. רמה 30 טיפוסית בשבועות 20–32 (כרגע 26.8). רמה 2 בפרק הראשון.
6. יהלומים טיפוסיים ≤ 6 בשבוע.
7. פרויקטים משפחתיים + קישוטים ≥ 30 שבועות טיפוסיים.
8. אף מחיר ב-K2 לא עולה על 90.
9. כל מבני השכונה לא נפתחים לפני שבוע 8 טיפוסי (`neighborhoodPacingAlarm`).
10. יומן עם 21 יום בלי פעילות, ואחריו שבוע טיפוסי: ההכנסה בשבוע החזרה שווה לשבוע טיפוסי ±5% (אין "קנס היעדרות" ואין
    "בונוס חזרה" כספי; §18 UC-04).
11. `fireLevel` מונוטוני על פני 3 עונות מדומות (אף פעם לא יורד; טבעת חדשה כל 10).
12. כל טריגר כלכלי משתלם לכל היותר פעם אחת לכל `(childId, skillId)` גם כשרמת 08 יורדת ועולה שוב (`paysOncePerSkill`).
13. בסימולציה של 10 שבועות עם חלונות שבת מ-hebcal (תל אביב וירושלים): אף grant של מטבע/יהלום/תיבה לאירוע שמפגשו התחיל בתוך
    החלון; מפגש שהתחיל לפני החלון משולם במלואו.
14. `skill_level_reverted` לעולם לא מייצר grant שלילי ולא משנה יתרה, תג או XP; `braveryLadderComplete` נותן בדיוק יהלום אחד
    לכל `(childId, ladderId)`; אף אירוע מרשימת D1a לא מייצר grant.
15. `offlineMission` + `makerProjectComplete`: ≤1 תיבה לכל `(childId, DayKey)`; `saveBonus` לעולם לא שלילי ו-0 בשבוע עם
    `minBalance < 0`.

## נספח א': `economy.config.json` (ברירות מחדל מלאות)

- **מיקום בריפו:** `packages/engine/economy/economy.config.json`.
- **ולידציה:** schema של zod (`EconomyConfigSchema`) יושב באותה תיקייה. נטען ב-build ונבדק ב-CI מול האינווריאנטים
  (§12.4).
- **עדכון:** אפשר לעדכן ב-OTA (E1, EAS Update). כל שינוי עובר דרך הסימולציה.
- **כללי ולידציה עיקריים:**
  - כל ערך מספרי ≥ 0.
  - `chests.triggers.*.gems` רק בטריגרים שמותרים לפי §16.3.
  - ל-`season.calendar` יש תאריכים רציפים שמתחילים ביום ראשון.
  - `shop.priceBands.K2.D[1] ≤ 90`.
  - `pets.needsDecay = false`, `pets.evolveBy = 'masteredSkillsInDomain'` (00-D4).
  - `campfire.fireLevel.resetsPerSeason = false` ו-`monotonic = true` (00-D4).
  - **בונוס החיסכון הוא המקור היחיד שתלוי בזמן** (00-D1): `jars.K1.saveBonus.capPerWeek` ו-`jars.K2.saveBonus.capPerWeek`
    חובה, סופיים (K1 ≤ 20, K2 ≤ 3); סריקת schema מוודאת שאין שום מקור אחר עם `basis`/`paidOn`/`perDay` תלויי זמן.
  - יהלומים (`gems > 0`) מותרים רק בטריגרים `skillMastered`, `bossDefeated`, `regionComplete`, `regionBossDefeated`,
    `familyGoalMet`, `holidayEventComplete`, `seasonFinalTier`, ו-`braveryLadderComplete` (K1 בלבד, 00-D1a: יהלום בסוף סולם
    שלא הוכרז). `level25or50.gems = 0`.
  - `antiGrind.neverEarns` מכיל את כל אירועי 00-D1a (`checkinDone`, `kindnessConfirmed`, `braveryStepDone`, `journalEntry`,
    `wonderAsked`) ואת `placementProbe`/`benchmarkLevel`; בדיקה סטטית שאף טריגר ב-`earn`/`chests` לא נושא את השמות האלה.
  - `earn.K1.stretchAttempt.enabledFor = ["K1"]`; אין `stretchAttempt` ב-`earn.K2`.
  - `chests.offlineMissionChestsPerDayMax = 1`.
  - `jars.*.saveBonus.basis = "minBalanceDuringWeekClamped0"` (אף פעם לא שלילי).
  - `capsuleMachine.nextCapsuleVisible = true`; אין מפתח `odds`/`weights` במקום כלשהו (00-D2).
  - אין מפתח בשם `discount`, `expires`, `availableUntil` או `streak` בשום מקום.
